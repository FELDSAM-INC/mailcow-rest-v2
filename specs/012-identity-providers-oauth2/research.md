# Research: Identity Providers and OAuth2 Clients

**Feature**: `specs/012-identity-providers-oauth2` | **Date**: 2026-10-18 | **Plan**: [plan.md](./plan.md)

This document settles the decisions that feature 012 adds. Every shared decision of feature 001
stays as it is and is referenced as "001 Rn": the Docker dev stack (001 R1), the schema fixture
(001 R2), tests on MariaDB and Redis (001 R3), the Laravel scaffold (001 R4), one connection and the
`restv2_` prefix (001 R5), sessions (001 R6), CSRF (001 R7), the request pipeline (001 R8),
`verify_hash` (001 R12), contract validation (001 R13), mailcow configuration (001 R14), sign-in
semantics, throttling and fail2ban (001 R16–R18), audit (001 R22), logs (001 R24) and problem URIs
(001 R27).

Precedence, as the owner set it: legacy behaviour first, then the constitution and
`docs/conventions.md`, then best practice. Legacy references are paths in mailcow-dockerized
`2026-09a` (`git -C ~/Projects/mailhosting show 2026-09a:<path>`). For this feature the FeldHost fork
differs only in the `sasl_log` service label and in branding texts (spec, "Legacy Parity").

Each entry has a **Decision**, its **Rationale** and the **Alternatives considered**.

## 1. Libraries and clients

### R1. OIDC client: `league/oauth2-client`

- **Decision**: `league/oauth2-client ^2.8` (MIT), the library legacy uses (2.7.0 there), with its
  `GenericProvider` for both Keycloak and generic OIDC, wrapped by
  `App\Clients\Oidc\LeagueOidcClient` behind the interface `App\Clients\Oidc\OidcClient`.
  - **Endpoints**: generic OIDC uses the three configured endpoints. Keycloak uses the endpoints of
    legacy's provider library (`stevenmaguire/oauth2-keycloak` 4.0):
    `<serverUrl>/realms/<realm>/protocol/openid-connect/{auth,token,userinfo}`, computed by
    `App\Clients\Oidc\OidcEndpoints::forKeycloak()`.
  - **Scopes**: Keycloak `profile email`, plus `openid` when `version_compare(version, '20.0.0',
    '>=')`, separated by a space (the Keycloak library's `getDefaultScopes()` and
    `getScopeSeparator()`). Generic OIDC sends the configured scope string unchanged, as legacy
    passes it to `GenericProvider` as a string.
  - **PKCE**: the provider option `pkceMethod: S256` (league 2.7+). After `getAuthorizationUrl()`
    the verifier comes from `getPkceCode()` and is stored in the pending single sign-on; before the
    exchange it is restored with `setPkceCode()`, so league adds `code_verifier`.
  - **State**: generated by the API (R5) and passed as the `state` option.
  - **Client authentication**: `client_secret_post` (league's default: `client_id` and
    `client_secret` in the form body), as legacy sends them.
  - **HTTP**: the Guzzle client is built by Laravel's HTTP client
    (`Http::timeout(7)->connectTimeout(7)->withOptions(['verify' => !$ignoreTlsErrors,
    'allow_redirects' => false])->buildClient()`) and handed to league as its `httpClient`
    collaborator. Requests therefore pass through Laravel's handler stack, so `Http::fake()` and
    `Http::assertSent()` work in tests without a custom fake.
  - **User details**: `getResourceOwner($token)->toArray()`, the user info response as an array, as
    legacy reads it. ID tokens are not validated, as in legacy.
  - **Errors**: `IdentityProviderException` (an OAuth error body or a 4xx) → "provider refused";
    `ConnectException`, a timeout or a 5xx → "provider unavailable" (R9 lists the cURL codes).
- **Rationale**: Legacy's own library gives the same request encoding, response parsing and error
  semantics, so a provider that works with the legacy UI works with the API. PKCE is built in. MIT
  is GPL-3.0-compatible. Laravel already depends on Guzzle, so the only new package is league's
  small core.
- **Alternatives considered**:
  - `stevenmaguire/oauth2-keycloak` (MIT), legacy's Keycloak provider: rejected. It only adds URL
    building and default scopes, both a few lines, and pulls in `firebase/php-jwt` for an
    encryption feature legacy does not use.
  - `jumbojett/openid-connect-php` (Apache-2.0): rejected. It validates ID tokens and uses discovery,
    so it would accept and refuse different providers than legacy does.
  - Laravel Socialite with Socialite Providers: rejected. It is built for server-rendered redirect
    callbacks, has no PKCE for generic providers, and adds two packages.
  - A hand-written flow on Laravel's HTTP client: rejected. It is feasible, but league already
    handles response parsing and PKCE exactly as legacy does.

### R2. LDAP client: the `ldap` PHP extension

- **Decision**: The PHP extension `ldap` (ext-ldap), added to `docker/php/Dockerfile`
  (`apk add openldap-dev` in the build stage, `docker-php-ext-install ldap`, and `libldap` at
  runtime), with a thin adapter `App\Clients\Ldap\ExtLdapDirectory` behind the interface
  `App\Clients\Ldap\LdapDirectory`. The adapter reproduces what legacy's `directorytree/ldaprecord`
  3.8 does for mailcow:
  - **URIs**: `ldap://host:port` or, with SSL, `ldaps://host:port`, where port 389 becomes 636
    (`HandlesConnection::makeConnectionUris`). Several hosts become one space-separated URI list
    passed to `ldap_connect()`, so they are tried in order. IPv6 literals are bracketed.
  - **Options**: `LDAP_OPT_PROTOCOL_VERSION` 3, `LDAP_OPT_REFERRALS` 0 (ldaprecord's
    `follow_referrals: false`), `LDAP_OPT_NETWORK_TIMEOUT` and `LDAP_OPT_TIMELIMIT` 7 s (FR-056; the
    library default is 5 s). With `ignoreTlsErrors`: `LDAP_OPT_X_TLS_REQUIRE_CERT` =
    `LDAP_OPT_X_TLS_NEVER` and `LDAP_OPT_X_TLS_NEWCTX`, as legacy passes in `options`.
  - **StartTLS**: `ldap_start_tls()` when `useStartTls` (never together with SSL).
  - **Service bind**: `ldap_bind(bindDn, bindPassword)`.
  - **User lookup**: `ldap_search(baseDn, filter, [usernameField, attributeField, displayname,
    distinguishedname, dn], 0, 1)`, where `filter` is `(&<configured filter>(<field>=<value>))`, or
    `(<field>=<value>)` without a configured filter (ldaprecord's grammar wraps several filters in
    `(&…)`). The value is `ldap_escape($username, '', LDAP_ESCAPE_FILTER)` (FR-030). Attribute
    names were validated when saved (letters, digits, hyphen).
  - **User bind**: `ldap_bind(entryDn, password)` on a new connection. An empty password is never
    sent (ldaprecord's `PasswordRequiredException`; it would be an anonymous bind).
  - **Results**: `LdapResult` with `verified(attributes)`, `wrongPassword` (result code 49),
    `unknownUser` (no entry), `unavailable(reason)` (connect, TLS, timeout, service bind refused,
    search error) and, for tests, `tlsFailure`. Codes come from `ldap_errno()` and
    `LDAP_OPT_DIAGNOSTIC_MESSAGE`.
  - **CA certificates**: the container's system bundle (`ca-certificates`), as php-fpm-mailcow
    uses its own. Operators with a private CA mount it and set `LDAPTLS_CACERT`, documented in the
    README.
- **Rationale**: The feature needs five LDAP calls. The extension is what ldaprecord uses
  underneath, so behaviour matches, and no PHP package is needed (constitution VIII). The interface
  is the fake in feature tests (constitution VII). An integration test against a real OpenLDAP
  server checks the adapter itself (quickstart Part A).
- **Alternatives considered**:
  - `directorytree/ldaprecord` (MIT), legacy's library: rejected. It is an ORM with model, scope
    and Active Directory layers; its `illuminate/contracts` constraint may lag Laravel 13; and the
    API uses none of its higher layers.
  - `symfony/ldap` (MIT): rejected. It is another abstraction whose query escaping and connection
    defaults differ from legacy's.

### R3. Keycloak service token and the mailpassword flow

- **Decision**: `App\Clients\Keycloak\HttpKeycloakAdminClient` (interface `KeycloakAdminClient`)
  on Laravel's HTTP client, and `App\Services\IdentityProvider\KeycloakServiceTokenCache`, a port
  of `identity_provider('get-keycloak-admin-token')`:
  1. Read the cached token from the `identity_provider` row `access_token`. When it is not empty,
     `POST <realm base>/protocol/openid-connect/token/introspect` with `token`, `client_id` and
     `client_secret`. Status 200 with `active: true` → reuse it.
  2. Otherwise `POST …/token` with `grant_type=client_credentials`, `client_id` and
     `client_secret`. Anything but 200 → `unavailable(serviceAccountRefused)`.
  3. Store the new token with `INSERT … ON DUPLICATE KEY UPDATE` on the row `access_token`, as legacy
     does. This upstream write belongs to the cache service.

  The mailpassword verification (`ProviderPasswordVerifier::verifyKeycloak()`, a port of
  `keycloak_mbox_login_rest`) then calls
  `GET <serverUrl>/admin/realms/<realm>/users?email=<username>&exact=true` with the bearer token:
  - a status other than 200 → `unavailable` (a 401 is retried once with a fresh token, because a
    cached token can expire between introspection and use; 403 means the `view-users` permission is
    missing);
  - an empty array → `unknownUser`;
  - no `attributes.mailcow_password[0]`, or an empty one → `notVerifiable`;
  - `LegacyPasswordVerifier::verify(hash, password)` (001 R12) false → `wrongPassword`;
  - otherwise `verified` with `mailcow_template[0]` as the mapping value and
    `trim(firstName . ' ' . lastName)` as the display name (FR-037).

  Every call uses the 7 s timeout and the TLS setting (FR-056). Legacy ignores the TLS setting for
  these calls; the spec states the deviation.
- **Rationale**: Sharing legacy's token row means the API, the legacy UI and the synchronisation job
  reuse one token, as today, and a save through either implementation clears it for all (FR-016).
  The configuration's version tag excludes the row (FR-050), so these writes never make an
  administrator's tag outdated.
- **Alternatives considered**: An API-owned token cache in Redis: rejected. It works, but it would
  fetch a second token per server, and the spec describes the cached token as shared legacy data.
  Not caching at all: rejected, because every password sign-in would cost two extra provider calls.

## 2. Single sign-on

### R4. Pending single sign-on, state, PKCE and return address

- **Decision**:
  - **Pending data**: the session key `restv2.sso` holds `stateHash` (hex SHA-256 of the state),
    `codeVerifier`, `returnUrl`, `type`, `issuedAt` and `expiresAt` (`issuedAt + 600 s`,
    `RESTV2_SSO_PENDING_TTL`). A new start replaces it. The first completion or provider-error
    report removes it, whatever its outcome, before the state is compared, so a state can never be
    tried twice. Comparison uses `hash_equals`.
  - **State**: 32 random bytes, base64url. Binding to the browser session follows from storing it
    in the session (`__Host-` cookie, 001 R6): a state from another browser has no pending entry
    there.
  - **Return address**: `https://<host><RESTV2_SSO_RETURN_PATH>`, default path `/ng/sso/return`, a
    route of mailcowui-ng (served under `/ng/`, 001 R23). `<host>` is the request's host name
    without port, lower-cased, when it is `MAILCOW_HOSTNAME` or one of the comma-separated
    `ADDITIONAL_SERVER_NAMES`; otherwise `MAILCOW_HOSTNAME`. `App\Services\IdentityProvider\AppReturnUrls`
    builds the list for the configuration read (primary first, duplicates and entries that are not
    valid host names dropped) and picks the one for a request. The scheme is `https`, configurable
    only for development (`RESTV2_SSO_RETURN_SCHEME`).
  - **Start response**: `200` with the authorization URL and `expiresAt`. Starting is a ceremony
    request and is not audited (plan, Complexity Tracking), like 001's challenges.
  - **SameSite**: the session cookie is `SameSite=Strict` (001 R6). The provider's redirect to
    `/ng/sso/return` is a cross-site navigation, so that page request carries no cookie, but it is a
    static page. The completion is a same-origin `fetch` from that page, which browsers send with
    Strict cookies. Quickstart Part C checks it in a real browser.
- **Rationale**: A single-use, short-lived, session-bound state with PKCE is the OAuth 2.0 Security
  BCP (RFC 9700). Hashing the state keeps it out of session dumps. Deriving the return address from
  the server's host names needs no stored setting and no upstream change (spec clarification 3).
- **Alternatives considered**: Storing state in a separate Redis key: rejected, the session already
  expires and is bound to the browser. A configurable return URL per host: rejected, it would need a
  new stored setting.

### R5. Completion, mailbox lookup and session

- **Decision**: `App\Services\IdentityProvider\SingleSignOnService::complete()`:
  1. Consume `restv2.sso`; missing, expired or mismatched → `401 sign-in-state-invalid`, audited
     (`signInStateInvalid`), provider not contacted.
  2. Load the current configuration (R8). Not Keycloak or generic OIDC, or incomplete →
     `409 single-sign-on-not-available`, audited.
  3. Exchange the code with the stored verifier and `redirect_uri = returnUrl`, then read the user
     details (R1). Refused → `401 sign-in-failed` (`providerRefused`); unreachable, timeout or 5xx →
     `503 identity-provider-unavailable` with `Retry-After: 30`.
  4. `email = strtolower(trim(details.email))`, which must pass `FILTER_VALIDATE_EMAIL`
     (`noEmailAddress` otherwise). Mapping value: `details.mailcow_template`, the first element when
     it is a list, `null` when it is neither a string nor a list of strings.
  5. Mailbox lookup as legacy (`kind NOT REGEXP 'location|thing|group'`, joined to `domain`).
     Existing → its `authsource` must be the configured type (`mailboxNotLinked`), then the
     template update of R6, then `mailbox.active = 1` and `domain.active = 1` (`accountInactive`).
     Missing → provisioning (R6).
  6. One database transaction: `RecentLoginRecorder::record()` (001, `sasl_log`, FR-024) and the
     `signIn` audit record (`authMethod: singleSignOn`, `details.identityProvider`,
     `details.mailboxCreated`, `details.templateApplied`). Then
     `SessionManager::promote()` with the principal `{username, mailboxUser, mailbox, singleSignOn,
     identityProvider: type, ssoLinkId}` and the session identifier renewed (001 R6). The provider
     link is stored (R7). `201` with `Location: /api/v2/session`.

  No second factor is asked for and `tfa` rows are not re-activated (FR-024). 001's
  `PendingActionEvaluator` returns no pending actions for a `singleSignOn` principal, which is the
  exception the spec makes to 001's FR-014 and FR-020. Failures are never published to fail2ban or
  counted by `SignInThrottle` (FR-028).
- **Provider error** (`reportProviderError()`, FR-063): steps 1 and 2 of the state check, then a
  `signIn` failure audit with `providerReturnedError` and `details.providerError` = the code, which
  the request schema limits to the RFC 6749 error character set and 64 characters. `204`.
- **Cancel** (`DELETE /session/single-sign-on`): removes `restv2.sso`, `204`, not audited, like
  001's `cancelPendingSignIn`.
- **Rationale**: This is a port of `identity_provider('verify-sso')` with the spec's deviations
  (state hardening, recent-login entry, configured type only, audit).
- **Alternatives considered**: Answering a refused exchange with `503`: rejected, the spec makes it
  the generic sign-in error. Auditing the start: rejected, see Complexity Tracking.

### R6. Mailbox creation and template updates, shared with feature 003

- **Decision**: `App\Services\IdentityProvider\MailboxProvisioner` is the only place where this
  feature changes mailboxes, and it delegates every write to feature 003's mailbox services, so that
  003's rules and side effects (alias, quota records, SOGo view, memcached flush, rate limit,
  tagged-mail handling, ACL rows, tags, follow-up step reporting) apply unchanged. 003's plan names
  those services; this plan refers to them as `MailboxService::create()` and
  `MailboxService::update()`.
  - **Template choice** (FR-035): the mapping entry whose attribute value equals the mapping value
    with `===` (spec: exact; legacy's loose `array_search` differs only for numeric strings), else
    the default template, else `noMatchingMapping`. The template row is looked up by name:
    `SELECT id, attributes FROM templates WHERE type = 'mailbox' AND template = ?` (legacy stores
    names in the mapping).
  - **Marker** (`App\Services\IdentityProvider\TemplateMarker`): `sha1(json_encode($attributesText))`,
    where `$attributesText` is the `templates.attributes` column as a string and `json_encode` uses
    PHP's default flags, exactly as legacy computes `attribute_hash`. It is stored in
    `mailbox.attributes.attribute_hash`.
  - **Creation** (FR-034 to FR-040): when `createMailboxOnSignIn` is off → `autoCreationOff`.
    Otherwise, under MariaDB `GET_LOCK('restv2_idp_' . sha1($email), 10)` (`docs/conventions.md`:
    uniqueness that upstream enforces only in code is protected with `GET_LOCK()`; the address must
    be unique across mailboxes and aliases), the mailbox is looked up again; if it now exists, the sign-in continues as for an
    existing mailbox (FR-040). Otherwise `MailboxService::create()` is called as the system actor
    (administrator-equivalent, no domain-administrator flags, like legacy's
    `access_all_exception`) with local part and domain from the address, the template's identifier,
    `authSource` = the configured type, no password, the display name of FR-037 (local part when
    empty) and the marker. 003 applies its rules: an existing primary domain, the address conflict
    rules, the domain limits, forced password change off for external sources and forced
    second-factor setup off for generic OIDC (003 FR-025). A refusal maps to
    `mailboxCreationFailed` with `details.cause` (`templateMissing`, `domainNotFound`,
    `addressInUse`, `mailboxLimitReached`, `quotaExceeded`, `validationFailed`). A duplicate-key
    error despite the lock is treated as "exists now".
  - **Update** (FR-025): only for an existing mailbox of the configured type whose mapping value
    matches an entry (never the default template) and whose template exists. When the stored
    marker equals the template's marker and `mailbox.name` equals the provider's name (after
    legacy's `ltrim(rtrim($name, '>'), '<')`), nothing happens. Otherwise
    `MailboxService::update()` applies the template's values as a change (quota, status, protocol
    access, TLS enforcement, quarantine notification and category, rate limit, user ACL, tags as
    003 defines "apply template"), sets the name, and records the new marker instead of clearing it
    (an option this feature adds to 003's change, which clears the marker otherwise, 003 FR-034). A
    failure is audited and the sign-in continues; a missing template skips the update.
  - **Audit**: 003's event types `mailboxCreation` and `mailboxUpdate` with target `mailbox`,
    actor = the signing-in user with `role: null` and `details.trigger: identityProviderSignIn`,
    `details.template`, `details.changes` and `details.signInRequestId` (FR-053).
- **Rationale**: The constitution makes 003's service the owner of mailbox writes. Reusing it keeps
  provisioning identical to legacy's `mailbox('add'|'edit', 'mailbox_from_template')`, which calls
  the same generic mailbox code.
- **Alternatives considered**: Writing `mailbox` rows here: rejected (constitution IV, duplicate
  logic). A database lock: rejected, the Redis lock spans the creation's follow-up steps too.

### R7. Provider tokens and renewal

- **Decision**:
  - **Storage**: the provider tokens are not kept in the Laravel session payload. They live in the
    Redis key `restv2:sso-link:<linkId>`, where `linkId` is 32 random hex characters kept in the
    session principal. The value is `Crypt::encryptString(json)` with `accessToken`,
    `refreshToken`, `expiresAt`, `lastRenewedAt`, `username` and `type`. Its TTL is
    `SESSION_LIFETIME`, renewed with the session. Sign-out (001 `SessionManager::end()`) and every
    session end delete it.
  - **Why a separate key**: Laravel writes the whole session at the end of each request. Two
    parallel requests at renewal time would otherwise write back a stale refresh token, and a
    provider with refresh-token rotation (Keycloak's "Revoke Refresh Token") would end the session
    on the next renewal.
  - **Renewal** (`IdentityProviderSessionGuard`): called by 001's `RequireAuth` for the modes
    `session` and `authenticated` when the principal's method is `singleSignOn`. On every such
    request it checks the local conditions of FR-026 (configuration still of the principal's type
    and complete; mailbox `authsource` still that type). When the link has a refresh token and
    `now - lastRenewedAt > 300 s` (`RESTV2_SSO_RENEWAL_INTERVAL`), it takes the lock
    `restv2:lock:sso-link:<linkId>` (10 s), re-reads the link, and if still due, calls
    `getAccessToken('refresh_token', …)` and the user info endpoint. A refused or failed renewal, or
    another e-mail address, ends the session. A response without a new refresh token keeps the old
    one (plan-level parity note: legacy stops renewing then). Without a refresh token at sign-in,
    only the local checks run (FR-026).
  - **Ending**: `SessionManager::end()`, delete the link, audit `identityProviderSessionEnd`
    (`details.reason`: `providerRefused`, `providerUnavailable`, `emailChanged`,
    `configurationChanged`, `authSourceChanged`, `providerLinkMissing`), answer `401 identity-provider-session-ended`.
  - **Security hardening (2026-10-22)**: a missing or unreadable provider link ends the session
    rather than disabling renewal. This is distinct from a valid stored link with no refresh
    token, whose existing local-check-only behavior is preserved. Browser-only heartbeat requests
    refresh the stored link's idle lifetime with the browser session without contacting the IdP.
  - `GET /session`, `DELETE /session` and public routes skip the guard, so a sign-out never
    depends on the provider and `GET /session` keeps 001's "never fails" rule.
- **Rationale**: Legacy refreshes on every page load of the user area; a 5-minute interval keeps the
  effect for a single-page app without a provider call per request (spec clarification 5).
  Encryption with the application key is defence in depth for tokens at rest in Redis, which other
  mailcow components can read.
- **Alternatives considered**: Renewing on every request: rejected, too many provider calls.
  Renewing in a background job: rejected, the API has no scheduler for user sessions and the
  session must end on the request that detects the failure.

## 3. Password sign-in through the provider

### R8. Extension of feature 001's password sign-in

- **Decision**: Feature 012 changes three classes of feature 001:
  - `AccountResolver::resolveForPassword()` tags a mailbox candidate with its `authsource`.
  - `PasswordSignInService` asks `App\Services\IdentityProvider\ProviderPasswordVerifier` for a
    mailbox candidate with source `ldap` or `keycloak`, instead of failing with
    `externalIdentitySource`. When no candidate matched (001's order; or role `mailboxUser` and no
    mailbox) and the configuration is LDAP, or Keycloak with the mailpassword flow, and complete,
    it asks the verifier with the username alone (FR-032), and on `verified` calls the provisioner
    (R6) before continuing.
  - The pending sign-in (001 `restv2.pending`) and the principal carry `passwordSource`
    (`mailcow`, `ldap`, `keycloak`), from which the method is derived: `directoryPassword[AndSecondFactor]`
    for LDAP, `providerPassword[AndSecondFactor]` for Keycloak.

  Outcome handling (FR-033):

  | Verifier result | HTTP | fail2ban | Throttle count | Audit reason |
  |---|---|---|---|---|
  | `verified` | continue as 001 (second factor, `tfa` re-activation, forced setup, `sasl_log`) | — | cleared | — |
  | `wrongPassword`, `unknownUser` | `401 sign-in-failed` | yes | yes | `invalidCredentials` |
  | `unavailable` | `503 identity-provider-unavailable`, `Retry-After: 30` | no | no | `identityProviderUnavailable` |
  | `notVerifiable` (no `mailcow_password`) | `401 sign-in-failed` | no | no | `passwordNotVerifiable` |
  | verified, creation impossible | `401 sign-in-failed` | no | no | `autoCreationOff`, `noMatchingMapping`, `mailboxCreationFailed` |
  | source cannot verify (generic OIDC, Keycloak without mailpassword flow, other type, incomplete) | `401 sign-in-failed` | no | yes (001 R16) | `externalIdentitySource` |

  - The throttle check (001 R17) runs first, so a throttled attempt never contacts the provider.
  - The username syntax check (001 R16) runs before the provider is contacted (FR-030).
  - The template update (R6) runs right after the provider verified the password and before the
    second-factor step, in legacy's order.
  - Forced second-factor setup is evaluated after a creation too (FR-039; legacy skips it).
  - Forced password change never applies, because 003 keeps it off for external sources.
- **Rationale**: This mirrors `user_login()`'s `keycloak` and `ldap` branches and the "user does
  not exist" branch, with the failure classification of the spec.
- **Alternatives considered**: A separate sign-in endpoint for provider passwords: rejected, the
  spec and legacy use the same form, and 001's role resolution order must apply.

## 4. Configuration

### R9. Storage codec of `identity_provider`

- **Decision**: `App\Services\IdentityProvider\IdentityProviderSettingsCodec` maps rows of
  `identity_provider` (`key`, `value`) to the value object `IdentityProviderConfig` and back.
  - **Keys per type** (legacy `identity_provider('edit')`):
    - all types: `authsource`, `ignore_ssl_error`, `login_provisioning`, `mappers`, `templates`,
      `default_template`, plus the cache row `access_token`;
    - Keycloak: `server_url`, `realm`, `client_id`, `client_secret`, `redirect_url`,
      `redirect_url_extra`, `version`, `mailpassword_flow`, `periodic_sync`, `import_users`,
      `sync_interval`;
    - generic OIDC: `authorize_url`, `token_url`, `userinfo_url`, `client_id`, `client_secret`,
      `redirect_url`, `redirect_url_extra`, `client_scopes`;
    - LDAP: `host`, `port`, `basedn`, `username_field`, `filter`, `attribute_field`, `binddn`,
      `bindpass`, `use_ssl`, `use_tls`, `periodic_sync`, `import_users`, `sync_interval`.
  - **Encodings written**, byte-identical to legacy's PDO bindings: `authsource` `keycloak`,
    `generic-oidc` or `ldap`; `ignore_ssl_error`, `login_provisioning`, `use_ssl` and `use_tls` as
    `'1'` or `''` (a PHP bool bound as a string); `mailpassword_flow`, `periodic_sync` and
    `import_users` as `'1'` or `'0'`; `sync_interval` and `port` as decimal strings; `host` as hosts
    joined by `,` without spaces; `mappers`, `templates` and `redirect_url_extra` as JSON lists with
    `json_encode` default flags (`[]` when empty); `default_template` as the name or `''`;
    `server_url` without trailing slashes; `username_field` and `attribute_field` lower-cased;
    `filter` and `attribute_field` as `''` when empty; `access_token` as `''`.
  - **Reading**: missing values take FR-007's defaults. Booleans are read with PHP truthiness (`''`
    and `'0'` false), as legacy's `boolval`/`intval`. JSON lists accept a list or an object (legacy's
    `array_filter` can produce `{"0":…,"2":…}`); values are taken in order. Mapping pairs beyond the
    shorter of the two lists are ignored. Empty strings are shown as `null`. Keys of another type
    are ignored.
  - **Whole save** (`PUT`): under `GET_LOCK('restv2_identity_provider', 5)`, so that two first saves
    cannot both answer `201`, one transaction that deletes every row whose key is not a key of the
    saved type (the `access_token` row included, then re-inserted as `''`), and upserts every key of
    the saved type with `INSERT … ON DUPLICATE KEY UPDATE value = VALUES(value)`. `created` and
    `modified` are left to their column defaults, as legacy does.
  - **Change** (`PATCH`): merge the patch into the current value object, validate the result as a
    whole save, then write it the same way.
  - **Delete**: `DELETE FROM identity_provider` in one statement, as legacy does.
  - **Completeness** (FR-008): Keycloak needs `server_url`, `realm`, `client_id`, `client_secret`,
    `redirect_url`, `version`; generic OIDC `client_id`, `client_secret`, `redirect_url`,
    `authorize_url`, `token_url`, `userinfo_url`; LDAP `host`, `port`, `basedn`, `binddn`,
    `bindpass`, each non-empty (legacy's truthiness in `identity_provider('init')`).
  - **Version tag**: strong ETag (001 `ETag`) over `key\0value\n` of every row except
    `access_token`, sorted by key, where the values of `client_secret` and `bindpass` are replaced
    by `hash_hmac('sha256', value, config('app.key'))` before hashing (FR-050,
    `docs/conventions.md`: a version tag never contains a plain hash of a stored secret).
  - **Last change**: `MAX(COALESCE(modified, created))` over the same rows, read through 001's
    `MailcowDateTime` cast.
- **Secret retention** (FR-014, `App\Services\IdentityProvider\SecretRetentionPolicy`): an omitted
  secret is kept only when the stored type equals the saved type and the normalised address equals
  the stored one (`server_url` after trailing-slash removal; `token_url` as given; `host` as the
  joined list). Otherwise `secretRequired` with `reason` `noStoredSecret`, `typeChanged` or
  `addressChanged` and `field`. The same policy serves the connection test (FR-019).
- **In-use checks** (FR-015, FR-017, `IdentityProviderUsage`): `SELECT authsource, COUNT(*) FROM
  mailbox WHERE authsource IS NOT NULL AND authsource <> 'mailcow' GROUP BY authsource`, the
  counts legacy's checks use. A type change is blocked by the counts of other types; a deletion by
  any count.
- **Normalisations** (FR-010 to FR-012): `useStartTls` is stored off when `useSsl` is on, and the
  response shows the effective values; duplicate additional return URLs are stored once in their
  first position.
- **Rationale**: Byte-identical encodings make the legacy UI, `mailcowauth.php` and the jobs read a
  configuration saved by the API exactly as one saved by legacy (FR-005, SC-002).
- **Alternatives considered**: Keeping other types' rows (legacy): rejected by the spec (FR-015).
  Storing booleans as `'0'`/`'1'` everywhere: rejected, legacy readers compare
  `ignore_ssl_error == "1"`, which works either way, but byte-identical storage keeps legacy UI
  round trips unchanged.

### R10. Validation

- **Decision**: Form Requests extending 001's `ApiFormRequest`, with rule objects that report the
  contract's rule codes:
  - `HttpUrl` (absolute, scheme `https` or `http`, host present, at most 2,000 characters, format
    `httpUrl`);
  - `KeycloakRealm` (1–255 characters, no `/`), `KeycloakVersion` (`^\d+(\.\d+){0,3}$`);
  - `ScopeList` (1–50 names of `[\x21\x23-\x5B\x5D-\x7E]`, single spaces);
  - `HostName` (a DNS name per RFC 1123, an IPv4 address or an IPv6 address, at most 253
    characters);
  - `LdapAttributeName` (`^[A-Za-z][A-Za-z0-9-]*$`, at most 255);
  - `LdapFilter` (at most 1,000 characters, starts with `(`, ends with `)`, parentheses balanced
    outside escapes);
  - `ExistingMailboxTemplate` (`notFound` with `resource: mailboxTemplate`; skipped for tests);
  - `UniqueAttributeValues` (`duplicate` with `duplicateOf`);
  - `RedirectUri` (an absolute URI with a scheme per RFC 3986, no fragment, no whitespace; format
    `redirectUri`) and the joined-length rule (`tooLong`, `max: 2000`, key `redirectUris`);
  - type-scoped members: any member that is not a writable setting of the request's (or the stored)
    type → `conflictsWith` with `field: type`, `value: <type>`; a different `type` in a `PATCH` →
    `immutable`;
  - `attributeField` empty while `importUsers` or `periodicSync` is on → `conflictsWith` with the
    field that is on.

  Every violation of a request is reported together (`docs/conventions.md`).
- **Rationale**: These are FR-010 to FR-013 and FR-044 with the shared rule codes.

### R11. Connection tests

- **Decision**: `App\Services\IdentityProvider\ConnectionTester`:
  - **Keycloak**: `POST <realm base>/protocol/openid-connect/token` with the client credentials
    grant. 200 → success. `invalid_client` or 401 → `credentialsRejected`. Other statuses →
    `unexpectedResponse` with the status (for example 400 `unauthorized_client` when the service
    account is off).
  - **Generic OIDC**: `POST <tokenEndpoint>` with `grant_type=authorization_code`, a random invalid
    `code`, `redirect_uri` = the legacy return URL and the client credentials. 2xx, or an error
    `invalid_grant`, `unauthorized_client`, `unsupported_grant_type` or `invalid_scope` → success
    (the client authenticated). `invalid_client` or 401 → `credentialsRejected`. Others →
    `unexpectedResponse`.
  - **LDAP**: connect with the candidate settings and bind with the bind DN and password
    (`LdapDirectory::testBind()`). Result code 49 → `credentialsRejected`; -1 with a certificate
    diagnostic, or a StartTLS failure → `tlsCertificateRejected`; -1 after the network timeout →
    `timedOut`; other connect failures → `unreachable`; other codes → `unexpectedResponse` with the
    code.
  - **HTTP transport errors** (cURL error numbers): 6, 7 → `unreachable`; 28 → `timedOut`; 35, 51,
    53, 54, 58, 59, 60, 64, 66, 77, 80, 82, 83, 90, 91 → `tlsCertificateRejected`.
  - `testedAddress` is the token URL or the LDAP URI list; `testedAt` is now. Redirects are not
    followed (R1), so a 3xx is `unexpectedResponse`.
  - Audited as `identityProviderConnectionTest`, outcome success or failure
    (`connectionTestFailed`, `details.failureCategory`, `details.testedAddress`, `details.type`).
- **Rationale**: The generic OIDC check follows the spec's deviation: an invalid code exchange makes
  the provider authenticate the client without issuing anything, which works for clients that only
  have the code flow. RFC 6749 §5.2 defines `invalid_client` for failed client authentication.
- **Alternatives considered**: Legacy's `OPTIONS` request: rejected by the spec. A client
  credentials grant for generic OIDC: rejected, many clients may not use it and would report a
  false failure.

### R12. Synchronisation status from the scheduled-job log

- **Decision**: It can be derived without changing legacy, with the limits below, so
  `App\Services\IdentityProvider\SynchronisationStatusReader` derives it (FR-062):
  - **Source**: the jobs push JSON entries `{time, priority, task, message}` onto the Redis list
    `CRON_LOG` (newest first), with `task` `Keycloak Sync` or `LDAP Sync`. dovecot-mailcow trims the
    list to `LOG_LINES` (9,999). The jobs' lock file `/tmp/iam-sync.lock` lives inside the php-fpm
    container and cannot be read.
  - **Scan**: `LRANGE CRON_LOG` in chunks of 500, newest first, keeping entries of the configured
    type's task, until a `DONE!` entry is found or 10,000 entries were read.
  - **Classification** of the 2026-09a texts: `DONE!` (info) ends a completed run; `Sync not ready
    (…)` and `Sync is already running` (warning) are scheduler ticks; `Creating user`, `Syncing
    attributes for user`, `Skipping user`, `Using default template`, `No matching attribute mapping`
    and `Could not create user` are per-user progress; any other `err` entry (for example
    `Received HTTP 401` or a database error) is a run-level failure.
  - **Derived values**: `lastCompletedAt` = time of the newest `DONE!`; `lastFailedAt` = the newest
    run-level failure newer than it; `running` when per-user progress or "already running" newer
    than the last `DONE!` lies within the last 120 s; `nextRunExpectedAt` = the first full minute at
    least `syncInterval` minutes after `lastCompletedAt`, or the next full minute after a failure
    (the lock file then holds no end time, so the next tick runs); `overdue` when that time is more
    than 120 s in the past and nothing newer was logged; `unknown` when no entry was found;
    `disabled` when neither import nor periodic synchronisation is on.
  - **Limits**, documented in the contract: an LDAP server that is unreachable when a run starts
    makes the job die before it logs anything, so such failures show only as `overdue`; a run of a
    directory larger than `LOG_LINES` users can push its previous `DONE!` out of the list while it
    runs; a release that changes the log texts needs the classification updated, which the parity
    suite per supported release catches (fixture `tests/fixtures/cron-log/2026-09a.json`).
  - The status is read per request, never cached, and not part of the version tag
    (`docs/conventions.md`).
- **Rationale**: Administrators asked to see whether synchronisation works (orchestrator item 2),
  and the log is the only signal the jobs leave that the API can read.
- **Alternatives considered**: Running the jobs in the API: out of scope (FR-018). Patching the jobs
  to write a status key: forbidden (constitution V). Leaving the status out: rejected, the
  derivation is reliable for completed runs and Keycloak failures.

## 5. OAuth2 clients

### R13. Client management on the legacy `oauth_*` tables

- **Decision**: `App\Services\Oauth2\Oauth2ClientService` owns every write to `oauth_clients`,
  `oauth_access_tokens`, `oauth_refresh_tokens` and `oauth_authorization_codes`.
  - **Creation**: `client_id = bin2hex(random_bytes(6))`, regenerated (up to 5 times) while it
    exists (spec edge case); `client_secret = bin2hex(random_bytes(12))`; `redirect_uri` = the URIs
    joined by single spaces after removing duplicates; `scope = 'profile'`; `grant_types` and
    `user_id` `NULL`, as legacy inserts. The identifier is the auto-increment `id`.
  - **Redirect URIs** are read by splitting `redirect_uri` on spaces and dropping empty parts, the
    way the OAuth2 server library splits several registered URIs.
  - **Change**: `UPDATE oauth_clients SET redirect_uri = ? WHERE id = ?`. `clientId` and `scope`
    must equal the stored values.
  - **Regeneration**: `UPDATE … SET client_secret = ?`. Tokens and codes are kept.
  - **Revocation**: in one transaction, count and delete the rows of the three token tables
    `WHERE client_id = ?`. Deletion does the same and then deletes the client.
  - **Counts**: `COUNT(*) … WHERE client_id = ? AND expires > NOW()` for access and refresh
    tokens. The `expires` columns are `TIMESTAMP`, written by the OAuth2 server library in mailcow's
    time zone; the API connection keeps the server's time zone (001 R5), so `NOW()` compares
    correctly. The list computes the counts for a page with two grouped queries, not one per row.
  - **List**: `q` → `client_id LIKE ? OR redirect_uri LIKE ?` (escaped, case-insensitive with the
    table's collation); `hasActiveTokens` → `EXISTS` on either token table; sort `id`, `client_id`,
    `redirect_uri`.
  - **Version tag**: strong ETag over `id|client_id|hmac|redirect_uri|grant_types|scope|user_id`,
    where `hmac` is `hash_hmac('sha256', client_secret, config('app.key'))` (FR-050,
    `docs/conventions.md`), so a regenerated secret changes the tag without the tag revealing it.
  - **Compatibility check**: `bshaffer/oauth2-server-php ^1.11` (MIT), the OAuth2 server library of
    legacy's `/oauth/*` endpoints, as a **dev** dependency. A feature test builds an
    `OAuth2\Server` on the test connection's PDO with legacy's grant types and lifetimes, and runs
    an authorization-code flow, a refresh and a resource request against clients managed through
    the API (SC-007).
- **Rationale**: Legacy's own storage format keeps the legacy UI and endpoints working (FR-049).
  Removing codes and tokens closes the gaps the spec lists (FR-047, FR-048).
- **Alternatives considered**: Soft-deleting clients: rejected, legacy has no such column.
  A hand-written token-endpoint simulation in tests: rejected, legacy's library is the authority on
  what its endpoints accept.

### R14. Bulk actions (FR-060, FR-061)

- **Decision**: `POST /oauth2-clients/bulk-actions` with `action` (`delete` or `revokeTokens`) and
  up to 100 `targets` (`Oauth2ClientBulkTarget`, extending `BulkTarget`), answered with
  `BulkResultResponse`.
  - The role and key-scope checks refuse the whole request (`403`).
  - Targets are deduplicated by `id`, keeping the first position.
  - Each target runs in its own transaction through the same service method as the single request,
    with the version check (`outdated`), `notFound`, `failed` on an unexpected exception, and one
    audit record carrying `bulkRequestId` (the request ID).
  - `version` is the ETag value without quotes, as `BulkTarget` defines.
  - There is no bulk secret regeneration: each new secret must be shown once and copied
    individually.
- **Rationale**: Legacy's OAuth2 table has the mass actions "Remove", "Revoke all client tokens"
  and "Generate new client secret" (`templates/admin/tab-config-oauth2.twig`), and
  `docs/conventions.md` requires bulk actions where legacy offers mass actions (orchestrator item).
- **Alternatives considered**: Two paths (`/bulk-deletion`, `/bulk-token-revocation`): rejected,
  one path with an action mirrors legacy's quick-action menu and keeps one schema.

## 6. Cross-cutting

### R15. Authorisation, audit and secrets

- **Decision**:
  - **Pipeline** (001 R8): the identity provider and OAuth2 routes use `restv2.auth:authenticated`
    (session or key), `restv2.csrf` and `restv2.pending:enforce`. Policies
    `IdentityProviderPolicy` and `Oauth2ClientPolicy` allow administrators only. Read-only keys
    are refused for every unsafe method by 001's `EnforceKeyScope`, which covers the connection
    test and the bulk action (`POST`). The single sign-on routes use `restv2.auth:browser`,
    `restv2.csrf` and `restv2.pending:allow`, so keys get `session-required`.
  - **Audited refusals** (`docs/conventions.md`, "Refusal auditing"): every state-changing route of
    the identity provider and OAuth2 modules declares
    `->defaults('restv2.audit', ['event' => …, 'target' => 'identityProvider'|'oauth2Client'])`, so
    the shared `App\Services\Audit\RefusalAuditor` (created by feature 002 or 008, the first
    implemented) records one failure record for every `4xx` refusal by an authenticated caller:
    policy (`permissionDenied`), read-only key (`insufficient-key-scope`) and restricted session
    (`pending-action-required`) refusals included, as well as validation (`validationFailed`),
    version (`versionOutdated`), in-use (`conflict`) and missing objects (`notFound`). CSRF failures
    and `401`s are not recorded. This feature registers two target resolvers:
    `IdentityProviderAuditTargetResolver` (null id, name = stored type) and
    `Oauth2ClientAuditTargetResolver` (the route's `oauth2ClientId` and its client ID, looked up
    without scope; for a bulk request a `null` target with `details.itemIds` and
    `details.bulkAction`). The connection test route declares `identityProviderConnectionTest`.
    Refusals raised inside the services (in-use, version) are not recorded twice: the services throw
    the problem and leave recording to `RefusalAuditor`. The single sign-on routes declare nothing:
    their failures are sign-in failures recorded by `SingleSignOnService`, and their pipeline
    refusals concern sign-in ceremonies, as for 001's sign-in routes.
  - **Details whitelist** per event type: changed settings with old and new values, where
    `client_secret`, `bindpass` and `access_token` appear only as `{"changed": true}`; test type,
    address and category; token and code counts; bulk request ID.
  - **Log redaction**: 001's `RedactSecrets` pattern already covers keys containing `pass`,
    `secret`, `token`, `code` and `authorization`; feature 012 adds `state`, `verifier`, `bind` and
    `cookie`. Provider HTTP bodies are never logged; errors log the status and the error code only.
  - **Secret scan**: a test (SC-004) runs every flow of this feature and greps responses, the
    captured log and the audit table for each secret, token, code, state and verifier used.
- **Rationale**: Constitution VI and FR-052 to FR-055.

### R16. Status codes

- **Decision**: `single-sign-on-not-available` is `409` (the server's state conflicts with the
  request); `sign-in-state-invalid` is `401`, like 001's `sign-in-expired`;
  `identity-provider-unavailable` is `503` with `Retry-After: 30` (`RESTV2_IDP_RETRY_AFTER`),
  justified like 001's `temporary-verification-failure`; `identity-provider-session-ended` is `401`;
  an outdated `If-Match` is 001's `412` `about:blank`. A whole save answers `201` with `Location`
  when it created the configuration and `200` otherwise (RFC 9110 `PUT`). The connection test and
  the other actions answer `200`.
- **Rationale**: Constitution II and the precedents of feature 001.

### R19. Parity notes added to the spec

These plan-level decisions differ from legacy in detail and are recorded in the spec's parity table
(constitution IV):

1. A renewal response without a new refresh token keeps the old one (legacy stops renewing) (R7).
2. Provider calls do not follow HTTP redirects (legacy's Guzzle default follows up to 5) (R1).
3. LDAP calls time out after 7 s, as every provider call (legacy library default 5 s) (R2).
4. IPv6 LDAP hosts are bracketed in connection URIs (legacy builds invalid URIs for them) (R2).

### R20. Capabilities reads (FR-064)

- **Decision**: `GET /capabilities/identity-provider` (`getIdentityProviderCapabilities`) and
  `GET /capabilities/oauth2-clients` (`getOauth2ClientsCapabilities`), following
  `docs/conventions.md`. Administrators and their keys, read-only included; not audited.
  - The identity provider read reports whether a configuration is stored and its type,
    `AppReturnUrls::all()` (so the setup flow can show the addresses to register before the first
    save, when `GET /identity-provider` still answers `404`), the types with what each offers, the
    FR-007 defaults, the FR-010 to FR-013 limits, `RESTV2_IDP_TIMEOUT` and the single sign-on
    lifetimes.
  - The OAuth2 read reports the fixed endpoint paths, the scope `profile`, the grant types that
    legacy's server registers (`authorization_code`, `password` through `UserCredentials`,
    `refresh_token`), the token lifetimes in effect, the 2,000-character redirect URI limit, the bulk
    limit and the page sizes. The lifetimes are legacy PHP configuration (`ACCESS_TOKEN_LIFETIME`,
    `REFRESH_TOKEN_LIFETIME` in `vars.inc.php`, overridable in `vars.local.inc.php`), so they come
    from 001's `MailcowConfig` (001 R14) with the export extended by these two names and the
    server settings `RESTV2_ACCESS_TOKEN_LIFETIME` and `RESTV2_REFRESH_TOKEN_LIFETIME` taking
    precedence; upstream defaults 86400 and 2678400.
- **Rationale**: The configuration read cannot serve a client before the first save, and the
  token lifetimes vary per server; both are what `docs/conventions.md` puts into capabilities reads.
- **Alternatives considered**: Returning the return addresses in a `404` body: rejected, a problem
  must not carry data. Hard-coding the lifetimes in the contract text: rejected, operators override
  them.
